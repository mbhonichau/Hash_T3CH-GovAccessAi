# GovAccess AI application review

**27 November 2026 · Checkout `991d447` · Readiness: blocked**

The current checkout fails to compile. The policy import, rules, publication, and assessment code is present, but the latest merge leaves authentication, intake, and audit implementations disconnected. Restoring compilation is the first step. An officer must then be able to open an assigned synthetic case, assess it using verified evidence and an immutable published policy, and record an audited official decision before the application can demonstrate its intended end-to-end workflow.

## Scope and verification

This review covers the Maven build, Spring configuration, Flyway history, controllers, services, Thymeleaf screens, and test sources. The working tree was clean at the start. Running `mvn -o test` produced six Java compilation errors, so the current checkout executed **zero tests**. The 52 passing tests and disposable PostgreSQL V14 results from the earlier Stage 4 verification apply to the earlier implementation. This review made no runtime code changes, started no application instance, and made no calls to Supabase or an AI provider.

## Findings by priority

### Blocker · The merged application fails to compile

`DashboardController` declares a `Principal` parameter without importing its type and uses four references to a removed `policies` field. Its constructor now injects `PolicyRecordAccessService` and `ApplicationIntakeService`. `WebSecurityConfiguration` constructs `ManagedAccountFilter(users)` using an undefined `users` variable. Restore the dashboard through its permission-checked services and wire the account filter to the account system selected for the merged application. [Dashboard controller](../src/main/java/za/gov/govaccess/dashboard/controller/DashboardController.java) · [Web security configuration](../src/main/java/za/gov/govaccess/security/WebSecurityConfiguration.java)

### High · Two account models and two permission vocabularies

`PersistentUserDetailsService` reads `user_account` and grants `PERM_*` authorities. The managed account configuration provides another `UserDetailsService` and password encoder, with roles such as Policy Administrator and authorities such as `POLICY_PUBLISH`. A second encoder is also defined in web security. The workspace exposes separate staff and managed-user administration screens. The merged configuration needs a single authentication path and an explicit mapping from accounts to the agreed role matrix. Bean selection, existing account access, and disabled-session behaviour require a real startup and login test. [Persistent authentication](../src/main/java/za/gov/govaccess/security/PersistentUserDetailsService.java) · [Managed authentication](../src/main/java/za/gov/govaccess/security/ManagedSecurityConfiguration.java) · [Managed role matrix](../src/main/java/za/gov/govaccess/security/ManagedRole.java)

### High · Case access lacks ownership and assignment enforcement

The intake service grants access via `PERM_APPLICATION_READ`, lists all cases, and loads detail by UUID. These operations have no record-level owner or assignment predicate. Detail includes applicant names, intake notes, evidence, and audit history. The managed role matrix assigns officers and supervisors case review authority, while applicants should only read their own cases. Enforce those boundaries in service queries as well as controllers. Test unrelated case IDs, owner access, officer reassignment, and the supervisor's permitted scope. [Intake service](../src/main/java/za/gov/govaccess/application/service/ApplicationIntakeService.java) · [Case detail screen](../src/main/resources/templates/application/details.html)

### High · Case creation conflicts with the append-only audit schema

Intake still saves a legacy `AuditEvent` with an inline action detail and actor username. V13 requires blank legacy text fields and populated chain metadata. This write path should fail against the migrated schema, rolling back intake creation. The case history screen also reads legacy fields whose values V13 moves into protected snapshots. Use the same transactional business audit append service for case creation and return an authorised case-history projection. Verify this with a create-case request on the fully migrated database. [Case creation](../src/main/java/za/gov/govaccess/application/service/ApplicationIntakeService.java) · [V13 audit migration](../src/main/java/za/gov/govaccess/rules/migration/V13__seal_policy_and_business_audit.java) · [Business audit service](../src/main/java/za/gov/govaccess/audit/service/BusinessAuditService.java)

### High · Case intake and assessment use separate persistence paths

The case screen reads the `assessment` table by application ID. The CSRF-protected assessment API accepts a programme, an application date, and assessor-supplied evidence, then writes `assessment_policy_run` and an audit event with no application ID. It verifies and pins the published policy hash, but its result does not populate the case's latest-assessment panel or the assigned officer's case audit history. The API persists the recommendation and policy pin. It does not persist the evidence revision, engine version or rule-by-rule result needed for a reproducible case assessment. Connect the case's programme and application date to the selector, derive inputs from stored verified evidence, and persist the policy and evidence references, engine version, rule outcomes, and recommendation in one case transaction. [Assessment service](../src/main/java/za/gov/govaccess/assessment/service/PublishedPolicyAssessmentService.java) · [Assessment run repository](../src/main/java/za/gov/govaccess/assessment/repository/AssessmentRunRepository.java) · [Case assessment reader](../src/main/java/za/gov/govaccess/application/service/ApplicationIntakeService.java)

### High · Competing migration recovery policies and broad demo data seeding

Two components provide Flyway migration strategies. One may repair a V5 checksum during startup after checking table shape. The other recognises specific externally installed migration entries. Reconcile them so a single strategy preserves known history and stops for unexpected drift. V7 also inserts synthetic intake and audit records as a normal migration. Confirm how those records should be handled on a non-demo database, and keep already applied migrations intact. Verify clean install, pre-Flyway adoption, existing V5–V7 deployments, and upgrade from V13 to V14 against disposable PostgreSQL. [Legacy history recovery](../src/main/java/com/hashtech/govaccessai/configuration/FlywayLegacyHistoryRecovery.java) · [Schema adoption](../src/main/java/za/gov/govaccess/configuration/FlywayLegacySchema.java) · [V7 synthetic data](../src/main/resources/db/migration/V7__synthetic_intake_cases.sql)

### Medium · Import recovery, document limits, and audit integrity

- **Policy jobs.** The PDF/text importer persists and claims jobs, and the review screen shows citations, rejected rules and edits. The worker polls queued work. The reviewed claim path has no lease expiry or reclaim path for a worker that stops after a job enters `RUNNING`. Add bounded recovery and test a restart mid-import. PDF extraction uses page text. Scanned documents still need OCR or a clear manual intake outcome. [Policy import worker](../src/main/java/za/gov/govaccess/policy/service/PolicyImportWorker.java) · [Import repository](../src/main/java/za/gov/govaccess/policy/repository/PolicyImportRepository.java) · [PDF reader](../src/main/java/za/gov/govaccess/document/service/PolicySourceReader.java)
- **Audit verification.** The chain hashes event metadata and snapshot references. It does not verify the contents of protected snapshots. An administrator-level edit to a payload after bypassing its database guard would therefore escape event-chain verification. Decide whether snapshot-content integrity is required and, if so, include its digest and test the complete chain. [Event hash](../src/main/java/za/gov/govaccess/audit/dto/BusinessAuditEvent.java) · [Chain verification](../src/main/java/za/gov/govaccess/audit/service/BusinessAuditService.java)
- **Policy review usability.** Policy Studio, imports and lifecycle screens exist. The lifecycle screen uses JSON for synthetic test cases and requires a UUID to name a superseded version. Structured test inputs and a programme-scoped version selector would let a reviewer complete publication without looking up internal IDs. [Lifecycle screen](../src/main/resources/templates/policy/lifecycle.html)
- **Accessibility and varied skill levels (pilot UX item).** The lifecycle page now offers a guided rule builder with catalogue fields and plain-language validation, while retaining an advanced JSON editor. Synthetic lifecycle tests still use a JSON textarea; import review uses a JSON-value field. Application declarations and document corrections are additional JSON entry points that could use guided inputs. The shared layout provides a skip link and visible keyboard focus, and these screens have associated labels, but this review did not include a WCAG contrast audit or screen-reader testing. Do not claim WCAG conformance until contrast is measured and keyboard and screen-reader flows are tested with assistive technology. [Lifecycle screen](../src/main/resources/templates/policy/lifecycle.html) · [Import review](../src/main/resources/templates/policy/import-review.html) · [Application intake](../src/main/resources/templates/application/create.html) · [Document review](../src/main/resources/templates/application/document.html)
- **Documentation.** Build and deployment notes cover the earlier policy workflow, while `AI_IMPLEMENTATION_PLAN.md` still describes earlier dependency assumptions. Bring the setup and role documentation into line with the merged code after choosing the account and migration paths. [Implementation plan](../AI_IMPLEMENTATION_PLAN.md) · [README](../README.md)

## Delivery order and acceptance checks

1. **Restore the merged baseline.** Repair the compile errors, select one account and migration path, run `mvn -o test`, then start a packaged app against fresh and upgraded disposable PostgreSQL. Confirm that all five roles can authenticate with the expected permissions.
2. **Secure and audit intake.** Prove an authorised user can submit a synthetic case and its chained audit event commits with it. Prove ownership and assignment controls, including an unrelated user requesting a known case ID.
3. **Close the case assessment workflow.** Assess a synthetic case using stored verified evidence. Display rule outcomes, recommendation, policy version and hash in the case screen. Publish a replacement and prove the earlier assessment stays pinned.
4. **Complete the official action.** An authorised officer records the decision. Cover a justified override and escalation where required. Confirm that applicant-facing output requires audited human approval.
5. **Run one controlled release rehearsal.** Exercise eligible, ineligible and needs-review cases. Verify database upgrade and rollback planning, audit tamper detection, recovery of interrupted imports, and one approved synthetic AI import against a disposable or approved environment.
